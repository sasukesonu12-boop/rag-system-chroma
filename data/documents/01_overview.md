# Northstar Learning Lab: Organization and Program Overview

## Purpose and operating model
Northstar Learning Lab is a fictional training organization used as a demonstration knowledge base for a Retrieval-Augmented Generation (RAG) application. Its policies, names, dates, budgets, and procedures are deliberately invented so that retrieval can be tested with facts that are not part of general model knowledge. This is a substantive sample corpus, not a claim about a real organization.

Northstar's mission is to help early-career learners build practical software and data skills through small projects, structured feedback, and evidence-based assessment. The lab operates three programs: Foundations, Applied Projects, and Career Launch. Foundations covers programming, version control, databases, and responsible technology. Applied Projects asks learners to build working artifacts in teams or individually. Career Launch focuses on portfolios, technical communication, and interview practice.

## Program principles
The lab values reproducibility, clear documentation, accessibility, and honest reporting. A learner should be able to explain what a project does, how it was built, what data it uses, what limitations it has, and how another person can run it. A polished interface is useful, but it does not compensate for a system that cannot be reproduced or whose claims cannot be verified.

The program uses evidence rather than attendance alone. Evidence can include a repository with a useful README, a short demonstration, tests, a data dictionary, an experiment log, or a written reflection on failures. Reviewers should distinguish between a feature that was implemented, a feature that was planned, and a feature that was only described.

## Roles
The Program Lead approves program policy and resolves escalated disputes. A Mentor gives technical feedback and helps learners reason through trade-offs without simply completing the work for them. A Reviewer checks deliverables against a rubric. Learners are responsible for asking questions early, maintaining their work, and disclosing the use of external code or AI assistance.

## Demonstration-only facts
The fictional program's internal code is NLL-27. The program lead role is assigned to Mira Sen. The lab's quarterly demo day is held on the second Friday of February, May, August, and November. The standard project review window is four business days. These facts are intentionally specific and are useful for the README's retrieval-versus-no-retrieval test.

## Governance
Northstar reviews its learning materials every quarter. Changes are recorded with a date, editor, reason, and summary of impact. A policy is not considered changed merely because a chat message suggested an edit; the approved version must be updated in the canonical document store. If two documents disagree, the application should surface the conflict rather than invent a resolution.

## Learner support and communication
Learners receive feedback through a shared project log. Questions should include the expected behavior, actual behavior, the smallest reproducible example, and what has already been tried. This structure helps mentors identify whether a problem comes from requirements, data, dependencies, code, or environment configuration. A question such as “my app is not working” is difficult to investigate because it provides no reproducible evidence.

The lab recommends short, regular updates instead of a long report at the end. Updates should state completed work, the next planned step, blockers, and any changes to the original plan. A blocker that affects a deadline should be raised as soon as it is recognized. The purpose of reporting is to make progress visible and enable early help, not to reward exaggerated claims.

## Inclusion and accessibility
Training material should use readable headings, define unfamiliar acronyms, and include examples that can be followed without paid software where practical. When a project has a visual interface, keyboard navigation and readable contrast should be considered. Accessibility is part of product quality because a tool that cannot be operated by its intended users does not meet its requirements.
